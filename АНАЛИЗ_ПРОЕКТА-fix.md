# Анализ проекта RiskiApp

Проверенный отчёт по статическому анализу репозитория. Исходного DDL базы данных, самой базы и работающего Windows-окружения в репозитории нет, поэтому выводы о SQL-схеме ниже отделены от того, что точно видно в C# и `DataSet1.xsd`.

## 1. Назначение и устройство

**RiskiApp** — настольное WinForms-приложение для ведения реестра рисков предприятия. Имя базы `РИСКИ_УЗТМ` указывает на конкретную организацию, но расшифровка и заказчик в репозитории не документированы.

Приложение позволяет:

- вести справочники периодов, подразделений, типов рисков, процессов, пользователей и мероприятий;
- создавать риски и записи о работе с рисками по периодам;
- хранить оценки вероятности и последствий до и после мероприятия;
- показывать текстовый уровень риска цветом;
- находить мероприятия с близкой датой окончания;
- экспортировать две основные таблицы в `.xlsx`.

**Стек:**

- .NET Framework 4.7.2 и Windows Forms;
- SQL Server через `System.Data.SqlClient`;
- типизированный ADO.NET `DataSet` и сгенерированные `TableAdapter`;
- ClosedXML 0.105.0 для записи `.xlsx`.

Отдельного application server/API нет: UI, загрузка данных, сохранение и прикладное форматирование находятся в одном WinForms-клиенте.

Решения `.sln`, DDL/миграций, тестов и документации по развёртыванию в репозитории нет.

## 3. Модель данных

В типизированном `DataSet` восемь таблиц:

| Таблица | Роль | Основные поля |
|---|---|---|
| `Периоды` | справочник периодов | `ID_Периода`, `НаименованиеПериода` |
| `Подразделения` | справочник подразделений | `ID_Подразделения`, `НаименованиеПодразделения` |
| `ТипыРисков` | категории риска | `ID_ТипаРиска`, `НаименованиеТипаРиска` |
| `Процессы` | бизнес-процессы | `ID_Процесса`, `НаименованиеПроцесса` |
| `Мероприятия` | меры по снижению риска | `ID_Меропрития`, `НаименованиеМероприятия` |
| `Пользователи` | сотрудники | ФИО, `Пароль`, подразделение, `IsАдминистратор`, должность |
| `Риски` | реестр рисков | описание, тип, причины, последствия, оценки, мероприятие, ответственный |
| `РискиДействия` | оценки и мероприятия в разрезе подразделения, процесса и периода | ссылки на справочники, дата, оценки до/после, эффективность |

Поля `УровеньРиска`, `УровеньРискаДоМП`, `УровеньРискаПослеМП` и `ЭффективностьМероприятия` помечены в клиентской схеме как read-only, не входят в `INSERT`/`SET` и, вероятнее всего, вычисляются в SQL Server. Без DDL нельзя утверждать, являются ли они именно computed columns, представлением или результатом иной серверной логики.

## 4. Реализованная функциональность

- Восемь вкладок, по одной на каждую таблицу.
- На каждой вкладке есть отдельное сохранение через соответствующий `TableAdapter.Update`.
- Для `Риски` и `РискиДействия` есть экспорт через ClosedXML.
- В видимых вычисляемых колонках уровень преобразуется в `Низкий`, `Средний` или `Высокий` и окрашивается.
- Кнопка `Проверка` выводит риски, дата мероприятия которых попала в заданный кодом интервал.
- Кнопка `Выход` вызывает `Application.Exit()`.

Формы входа и проверок роли `IsАдминистратор` нет: `Program.Main` сразу открывает `Form_Главная`.

## 5. Подтверждённые проблемы

### Критичные: доступ и учётные данные

1. **Нет прикладной аутентификации и авторизации.** Клиент не запрашивает логин/пароль и не ограничивает вкладки или операции по `IsАдминистратор`. При этом нельзя говорить, что доступ получит буквально любой запустивший EXE: `Integrated Security=True` подключает SQL Server от имени текущей Windows-учётной записи, и сервер всё ещё может отказать ей в доступе. Точный вывод: любой Windows-пользователь, которому SQL Server уже разрешает подключение с достаточными правами, получает весь интерфейс приложения без дополнительной проверки роли.

2. **Колонка `Пароль` открыта в редактируемом гриде.** Она представлена обычным `DataGridViewTextBoxColumn`, без маскирования, а рядом доступен для редактирования флаг администратора. В C# нет хеширования или проверки пароля. Однако по одному `nvarchar(200)` нельзя строго доказать, что реальные значения в базе являются открытым текстом: это проверяется только по данным/DDL/коду, который их создавал. В любом случае UI раскрывает сохранённое значение всем допущенным к приложению и позволяет заменить его произвольной строкой. Для реальных паролей это не соответствует рекомендациям по хранению адаптивного salted hash.

3. **Строка подключения рассчитана на локальный именованный экземпляр.** `Data Source=.\sqlexpress` означает SQL Express на той же машине. Строка находится не «вшитой в код», а в `App.config`, поэтому после поставки её можно заменить. Текущая конфигурация всё же не описывает централизованное многопользовательское развёртывание. `TrustServerCertificate=True` сохраняет шифрование канала, но отключает проверку цепочки доверия сертификата.

### Серьёзные: схема и сохранение

4. **У `РискиДействия` нет ключа в клиентском DataSet.** Семь других таблиц имеют `xs:unique msdata:PrimaryKey="true"`, эта таблица — нет. Это точно означает отсутствие `DataTable.PrimaryKey` и уникальности на клиенте. Так как запрос является простым `SELECT ... FROM РискиДействия`, это также сильный признак отсутствия распознанного PK в SQL Server, но без DDL это не доказано окончательно.

   Сгенерированные `UPDATE` и `DELETE` идентифицируют строку по большому набору исходных значений; `DELETE` сравнивает все 15 полей, включая read-only. Это реализация optimistic concurrency, а не правило «при наличии PK сравнивается только PK»: у остальных адаптеров в `WHERE` тоже есть PK **и** исходные значения других колонок. Если SQL-таблица допускает две полностью одинаковые записи, одна команда может затронуть обе. Любое серверное изменение сравниваемого поля после загрузки способно привести к нулю затронутых строк и `DBConcurrencyException`.

   У таблицы нет отдельного ID в клиентской схеме и нет возврата `SCOPE_IDENTITY()`. Поэтому клиент не имеет стабильного идентификатора строки; отсутствие `SCOPE_IDENTITY()` здесь является следствием отсутствия identity-поля, а не самостоятельной ошибкой получения существующего ID.

5. **Ошибочная relation процесса.** В `DataSet1.xsd` и сгенерированном коде relation `Процессы_РискиДействия` связывает `Процессы.ID_Процесса` с `РискиДействия.ID_Периода`. Дочерним ключом должен быть `ID_Процесса`. Relation создана с `createConstraints: false`, поэтому она не валидирует записи, но навигация `GetChildRows`/parent-row по ней возвращает логически неверные данные.

6. **Справочник мероприятий загружается в другой экземпляр DataSet.** Большинство таблиц находятся в `dataSet1`, а `Мероприятия` — в `dataSet11`. Поэтому relations `Мероприятия -> Риски` и `Мероприятия -> РискиДействия` внутри основного `dataSet1` не могут найти родителей: его таблица `Мероприятия` остаётся пустой. ComboBox работает, потому что его `BindingSource` отдельно смотрит в `dataSet11`, но объектная модель DataSet становится внутренне неполной. `dataSet12` и `dataSet13` только создаются и не используются.

7. **Нет общей транзакции и возможны частичные сохранения.** Каждая кнопка вызывает только один адаптер, а сгенерированный `TableAdapterManager` не используется. Кроме того, `DataAdapter.Update` выполняет команды по строкам последовательно, не как единый batch/transaction: если поздняя строка завершится ошибкой, ранние могли уже сохраниться. Для связанных добавлений порядок и перенос сгенерированных ID тоже остаются обязанностью UI.

8. **Исключения загрузки и сохранения не обрабатываются.** В `Form_Load` и восьми обработчиках `Сохранить` нет `try/catch`; глобальные `Application.ThreadException` и `AppDomain.UnhandledException` не подключены. Ошибка соединения, constraint или concurrency доходит до стандартной обработки WinForms и может оставить приложение/данные в неопределённом или частично сохранённом состоянии.

### Логика UI

9. **В `Проверка` возможен `NullReferenceException`/`InvalidCastException`.** После проверки даты код без проверки берёт и приводит к `int` значения риска и мероприятия. Незаполненная новая строка с датой либо значение неожиданного типа приводит к исключению.

10. **Проверка срока использует `TimeSpan.Days`, а не точную/календарную границу.** Условие `difference.Days < 14 && difference.Days >= 0` работает с усечённым целым числом дней. Из-за этого уже наступившая сегодня полночь может иметь `Days == 0` и попасть в список, а смысл границы зависит от времени запуска. Следует явно выбрать правило: календарные даты (`endDate.Date`) или точные 14 суток (`TotalDays`).

11. **Логика цвета содержит противоречивый, но сейчас скрытый код.** Для числовых колонок заданы пороги `<3 / <6 / >=6` в `РискиДействия` и `<3 / <7 / >=7` в `Риски`; для текстовых — `1..2 / >2..4 / >4`. Однако числовые колонки на `Form_Load` скрываются. Поэтому прежний вывод о двух одновременно видимых цветах в одной строке неверен: пользователь видит только одинаковую текстовую шкалу `1–2`, `(2–4]`, `>4`. Проблема остаётся как мёртвая и противоречивая логика, которая проявится при повторном показе числовых колонок.

12. **Нет доменной валидации оценок.** Типизированная схема задаёт только `decimal`; UI не ограничивает минимум, максимум и допустимый шаг. Для `0`, отрицательных значений и `null` текстовая категория не устанавливается. Допустимую шкалу нельзя восстановить из репозитория, её нужно зафиксировать как бизнес-правило и constraint в БД/UI.

### Экспорт

13. **Экспорт включает скрытые колонки.** Циклы проходят по всем `dgv.Columns` и не проверяют `Visible`. Поэтому в файл попадают скрытые технические ID и скрытые числовые уровни, хотя на экране их нет. `FormattedValue` действительно даёт отображаемый текст для ComboBox, но не гарантирует отсутствие raw ID в обычных скрытых колонках.

14. **Все значения превращаются в строки.** Вызов `FormattedValue?.ToString()` записывает числа и даты в Excel как текст, что мешает сортировке, формулам и числовому форматированию. Для ComboBox имеет смысл экспортировать display text, но числа и даты следует передавать в ClosedXML типизированными значениями.

15. **Проверка пустого грида ненадёжна.** При разрешённой строке добавления `Rows.Count` может быть равен 1 даже без данных; затем эта строка пропускается через `IsNewRow`, и создаётся пустой файл вместо сообщения `Нет данных`.

16. **Комментарий об автоподборе ширины неверен.** `worksheet.Columns().Width = 40` задаёт всем колонкам фиксированную ширину. Автоподбор ClosedXML выполняется методом `AdjustToContents()`.

### Технический долг

17. Опечатка `ID_Меропрития` присутствует в SQL-именах и сгенерированном API, тогда как связанные поля используют правильное `ID_Мероприятия`.
18. В `.csproj` остались неиспользуемые COM-ссылки на Excel/Office/VBIDE и неиспользуемый alias `Excel`. Экспорт работает через ClosedXML. `COMReference` разрешается MSBuild через реестр build-машины, поэтому сборка зависит от наличия подходящих зарегистрированных type libraries/wrappers; формулировка «обязательно нужен установленный Office» слишком категорична, поскольку возможны заранее созданные wrapper assemblies и иные способы регистрации.
19. Поле `рискиTableAdapter` не используется; реально работает `рискиTableAdapter1`.
20. Классификация уровня риска продублирована трижды, есть пустые обработчики событий и дизайнерские артефакты.
21. Автоматических тестов нет; особенно не покрыты пороги риска, сроки, экспорт и ошибки сохранения.

## 6. Итог и приоритеты

Приложение похоже на рабочий внутренний прототип CRUD-реестра. Основной сценарий реализован, но перед эксплуатацией с чувствительными корпоративными данными приоритеты должны быть такими:

1. определить реальную модель доступа: Windows/SQL-права либо прикладная аутентификация, роли и аудит;
2. проверить фактическое содержимое `Пароль`, удалить его показ из грида и внедрить корректное хранение, если это действительно пароль;
3. добавить стабильный PK для `РискиДействия` в БД и обновить DataSet/TableAdapter;
4. исправить relation процесса и объединить таблицы в одном экземпляре DataSet;
5. сделать сохранение транзакционным там, где операция охватывает связанные записи, и нормально показывать ошибки;
6. утвердить одну шкалу риска и валидировать диапазоны в UI и SQL Server;
7. исправить экспорт скрытых колонок и типов Excel;
8. добавить тесты прикладной логики, отделив её от формы.
